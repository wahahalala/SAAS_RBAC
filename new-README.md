### Frontend architecture

The web app follows one rule: **fetch where the data is needed, mutate on the
server**. Client state is only for what the browser itself owns.

| Concern | Mechanism | Where |
|---------|-----------|-------|
| Server data fetch | React Server Components | `lib/server/api.ts` (`serverFetch`), read directly in `page.tsx` |
| Mutations | Server Actions | `app/actions/*` |
| BFF / streams (downloads, polling) | Route Handlers | `app/api/**/route.ts` |
| Client-side server state (polling) | TanStack Query | `components/dashboard/reports-panel.tsx` |
| UI state | Zustand | `lib/stores/ui-store.ts` |
| Interface language | Cookie + dictionary | `lib/i18n/*`, switched by `app/actions/locale.ts` |

Consequences worth knowing:

- **No page is a Client Component.** A `"use client"` page cannot fetch on the
  server, which forces a skeleton and a browser round trip. Pages render their
  data in the initial HTML; only interactive leaves (dialogs, menus, forms) are
  client components. `test/architecture.spec.ts` asserts this.
- **No `useEffect` data fetching.** The pattern is gone; only DOM/subscription
  effects remain (keyboard shortcuts, sidebar). Also asserted by that test.
- **Server data is never duplicated into a client store.** `auth-store` and
  `tenant-store` were deleted — they held the user and the tenant list, which
  created a second source of truth that could drift from the server. Zustand now
  holds only UI preferences.
- **The active tenant is a cookie, not localStorage.** Server Components must
  scope their fetches by tenant, and only a cookie is readable on the server.

### Internationalisation (English / 中文)

The interface ships in **English (`en`, default) and Simplified Chinese (`zh`)**,
switchable from the button in the top-right of the dashboard header, the auth
pages and the landing page.

The language is a **cookie** (`saas.locale`) resolved on the server, for the same
reason the tenant is: the copy is rendered by Server Components, so a
client-only language store would produce a flash of English and a hydration
mismatch. Picking a language runs a Server Action (`app/actions/locale.ts`) that
writes the cookie and revalidates the layout, so the whole tree re-renders with
the new dictionary. `<html lang>` follows the locale, which keeps screen readers
and font selection correct.

```
lib/i18n/
├── config.ts             # LOCALES ('en' | 'zh'), default, endonym labels
├── dictionaries/en.ts    # the reference dictionary; Dictionary type is derived from it
├── dictionaries/zh.ts    # typed as Dictionary -> a missing key is a compile error
├── locale-cookie.ts      # SERVER ONLY (next/headers)
├── index.ts              # SERVER ONLY: getDictionary() resolve the active dictionary
└── format.ts             # CLIENT SAFE: Dictionary type + interpolate()
```

Two rules keep this working:

1. **Client Components import from `lib/i18n/format`, never `lib/i18n`.** The
   index module reads `cookies()`, and `next/headers` cannot be bundled for the
   browser — importing it from a Client Component fails the build with
   *"You're importing a component that needs next/headers"*. Client components
   receive their dictionary slice as a **prop** from a Server Component page.
2. **`zh.ts` is annotated `Dictionary`,** which is the widened shape of `en.ts`,
   so translating a new key is forced rather than remembered. `test/i18n.spec.ts`
   additionally asserts identical leaf structure, no untranslated leftovers and
   matching `{placeholder}` sets between locales.

Adding a locale = add a `zh`-style dictionary, register it in `lib/i18n/index.ts`
and `config.ts`. Adding a string = add it to `en.ts` first (type-check then
points at every locale that still needs it).

#### How server rendering authenticates

```
browser ──▶ Next.js ──▶ /api/auth/* route handler ──▶ NestJS API
                │              │
                │              └─ rewrites the refresh cookie's Path to "/"
                │
                └─ Server Components call POST /api/auth/session  (access token only,
                                                                    refresh token NOT rotated)
```

Two non-obvious pieces make this work:

1. **The refresh cookie's Path is rewritten to `/`.** The API sets it at
   `/api/v1/auth`; proxied unchanged, the browser would only send it on those
   requests, so a Server Component rendering `/dashboard` would never see it and
   every protected page would render as signed out. `app/api/auth/[...path]` is a
   Route Handler (not a rewrite) precisely because a rewrite cannot alter
   `Set-Cookie`. The API is untouched, so direct clients keep working.
2. **Server rendering uses `/auth/session`, not `/auth/refresh`.** `/refresh`
   *rotates* the refresh token, but a Server Component cannot persist the new
   cookie — the rotated token would be lost and the next render would present a
   revoked one. `/auth/session` mints an access token and leaves the refresh
   token alone. Rotation still happens from the client, where the cookie can be
   stored.

### Tenant flow (API ↔ web)

Every tenant-bound request carries `X-Tenant-Id`; `TenantGuard` resolves it and stores the tenant on the request so `TenantInterceptor` can open the AsyncLocalStorage context.

| Route | Tenant scope |
|-------|--------------|
| `GET /users/me/organizations` | user-level — `@SkipTenantCheck()`, returns each membership's `tenantId` |
| `GET /auth/me`, `PATCH|DELETE /users/me` | user-level — `@SkipTenantCheck()` |
| `POST /organizations` | provisioning — `@SkipTenantCheck()` (no tenant exists yet) |
| `GET /auth/me/permissions`, `GET /organizations/:slug`, … | tenant-scoped — `X-Tenant-Id` required, else `403` |
| `POST /auth/session` | public, refresh cookie only — mints an access token WITHOUT rotating the refresh token (used by server rendering) |

The web client marks each call accordingly (`api-client.ts` → `tenantScoped`), resolves the active tenant in `useActiveTenant()` (keep the persisted one when still valid, otherwise fall back to the first organization), clears it on logout, and drops tenant-scoped React Query caches when the tenant changes.

Organization routes take a **slug**, not a tenant id, so the slug is always resolved *within* the request's tenant (`OrganizationsService.findBySlugInTenant` / `getMembership`). Without that binding a user who belongs to two tenants could send tenant A's `X-Tenant-Id` and operate on tenant B's organization.

### Invitation flow

```
Admin invites (POST /organizations/:slug/invitations)
        |
        v
Invitation row  (status: pending, token, expiresAt = now + 7d)
        |
        v
BullMQ emailQueue  -- job "invite-email" -->  worker EmailProcessor
        |
        v
Invitee opens /invitations/{token}   (public preview: org, role, inviter)
        |
        v
POST /invitations/{token}/accept  -->  Membership created, status = accepted
```

Status lifecycle — `pending` → `accepted` | `expired` | `canceled`:

| Transition | Trigger |
|------------|---------|
| `pending` → `accepted` | the invitee accepts |
| `pending` → `expired` | `expiresAt` has passed; applied lazily on read/write (no scheduler), and persisted by the admin list |
| `pending` → `canceled` | an admin revokes it (`DELETE /organizations/:slug/invitations/:id`) |

Behaviour worth knowing:

- **The token is the credential.** Accepting does not require the signed-in email to match the invited address. A token is single-use: only the account that accepted it may re-accept (idempotent for a double-click / refresh); anyone else is refused.
- **Both accept routes are `@SkipTenantCheck()`** — the token is the tenant selector, and a brand-new invitee has no active tenant yet.
- **Email enqueue failures are logged, not thrown**: the invitation still exists and the admin can retry.
- BullMQ rejects custom job ids containing `:`, so ids are built with `-` (a colon silently broke every invite enqueue).

### Domain events

Business facts are emitted as domain events so side effects (email, audit,
analytics) do not have to be wired into the services that own the writes.

| Event | Emitted by | When |
|-------|-----------|------|
| `user.created` | `AuthService.register` | after the account commits |
| `tenant.created` | `OrganizationsService.create` | after the provisioning transaction commits |
| `role.changed` | `OrganizationsService.updateMemberRole` | after the role update, only on a real transition |
| `report.completed` | worker `ReportRunnerService` | after the report row is marked completed **or** failed |

Listeners (`apps/api/src/modules/events/listeners`):

| Listener | Side effect |
|----------|-------------|
| Email | enqueues the welcome email (skipped for invitation-created accounts — they already get an invite) |
| Audit | writes `AuditLog` (the model previously existed with **no writer anywhere**) |
| Analytics | writes `UsageRecord` (`event.<name>` metrics, so they surface in the usage report) |

Rules the implementation follows:

- **Emit after the write commits, never inside a transaction.** A rolled-back provisioning must not have announced a tenant, and a listener reading the row must see it.
- **`tenantId` is always in the payload, never read ambiently.** Listeners run asynchronously, after the request's AsyncLocalStorage context is gone, so an ambient read would mis-attribute rows. `USER_CREATED` carries `null` (registration creates an account before it belongs to any tenant), which is why `AuditLog.tenantId` is nullable.
- **A listener failure never breaks the request** whose write already succeeded; `DomainEventsService.emit` catches and logs.
- **A missing listener side effect never overrides a success.** The report runner publishes outside its try/catch: if publishing fails, the generated report stays `completed` instead of being rewritten to `failed` (which would also make BullMQ regenerate a file that exists).

#### Cross-process bridge

Nest's `EventEmitter` is in-process only, but `REPORT_COMPLETED` is produced by the **worker**. Rather than duplicating listeners there, the worker publishes to `domainEventQueue` and the API's `DomainEventBridgeConsumer` re-emits it locally — so listeners live in exactly one place:

```
worker ReportRunnerService
   └─ DomainEventPublisher  ->  BullMQ domainEventQueue  ->  API DomainEventBridgeConsumer  ->  local EventEmitter  ->  Audit / Analytics / Email listeners
```

### Audit trail

Every auditable action is written to `AuditLog` by the audit domain-event
listener, and read back through `GET /audit-logs`.

| Action | Recorded when |
|--------|---------------|
| `LOGIN` | credentials or OAuth sign-in succeeded |
| `LOGOUT` | a session was actually revoked (single device or all devices) |
| `CREATE_USER` | an account was created |
| `DELETE_USER` | an account was deleted |
| `CHANGE_ROLE` | a member's role changed (only on a real transition) |
| `EXPORT_DATA` | a report artifact was **downloaded** (bytes actually served) |
| `CREATE_TENANT` | a tenant was provisioned (kept from the event work) |
| `REPORT_COMPLETED` | a report finished generating, successfully or not |

Action names live in `AUDIT_ACTIONS` (`@saas/shared-types`) rather than as
string literals at each call site: the query API filters *by* action, so a typo
would silently create an action no filter can find.

```
GET /audit-logs?page=2&limit=50&action=EXPORT_DATA&from=2026-01-01&search=alice
```

| Parameter | Effect |
|-----------|--------|
| `page`, `limit` | 1-indexed pagination, `limit` capped at 100 |
| `action` | one of the action names; an unknown value is a 400, not an empty page |
| `userId` | entries performed by that actor |
| `entity`, `entityId` | entries about a particular record |
| `from`, `to` | inclusive `createdAt` range (a date-only `to` covers the whole day) |
| `search` | free text over action, entity, entity id, IP and the actor's email/name |

Behaviour worth knowing:

- **Requires `audit.read`** (administrator capability) and an active tenant. The
  permission is granted to `admin`; `prisma/seed.ts` also re-syncs it onto
  already-provisioned tenants' admin roles, which otherwise would never receive a
  permission added later.
- **Tenant-less entries are not served to a tenant.** A `LOGIN` or `CREATE_USER`
  happens before a tenant exists (`tenantId` is null), so including it in a
  tenant's list would leak activity about accounts that may not belong to it.
  Filtering cannot widen the result either — the tenant is the first clause in
  the query.
- **Ordering is `(createdAt desc, id desc)`.** Ordering by timestamp alone makes
  pagination unstable: entries written in the same millisecond would repeat on
  one page and vanish from the next.
- **`metadata`, `ipAddress` and `userAgent` are recorded per action.** Request
  metadata is carried in the *event payload* rather than read by the listener,
  which runs after the request is gone; worker-produced facts (report
  completion) have no request and record `null`.
- **The trail survives user deletion.** `AuditLog.userId` is `SetNull`, and
  `DELETE_USER` captures the deleted identity in `metadata`, so the record of the
  deletion outlives the account.

### Report generation (async)

```
Client  POST /reports {type, format}
           |
           v
        Report row (status: pending)          <- created FIRST, so the id is stable
           |
           v
        BullMQ reportQueue -- job "generate-report" --> worker ReportProcessor
           |                                               |
           |                                        ReportRunnerService
           |                                         ├─ ReportDataService  (tenant-scoped query)
           |                                         ├─ csv.writer / pdf.writer
           |                                         └─ ReportStorageService (disk)
           v
        Report row → completed (+ filePath/fileName/fileSize/rowCount)
           |
           v
Client polls GET /reports/:id → status → GET /reports/:id/download (streamed)
```

Status lifecycle: `pending` → `processing` → `completed` | `failed`.

| Type | Source data | Columns |
|------|-------------|---------|
| `usage` | `UsageRecord` grouped by metric | Metric, Total Quantity, Records |
| `members` | `Membership` + `User` + `Role` | Name, Email, Role, Joined At |
| `billing` | `Subscription` | Plan, Status, Cancel At Period End, + period dates |

Behaviour worth knowing:

- **The row is written before the job is enqueued.** If Redis is unavailable the report is marked `failed` with the reason instead of leaving the client polling forever. A second identical request while one is in flight is rejected with 409.
- **`filePath` is never returned to clients.** Downloads go through `GET /reports/:id/download`, which re-checks the caller's tenant, so knowing an id is not enough to read another tenant's report.
- **The artifact directory is shared between two processes**: the worker writes it, the API reads it. Both must resolve the same `REPORTS_DIR` (this is exactly why the default `process.cwd()`-relative path is not enough when they run as separate containers — mount a shared volume).
- All report routes require the `billing.manage` permission and an active tenant (`X-Tenant-Id`).
- PDF is rendered with `pdfkit` (pure JS — no headless browser); the UI polls only while something is still pending or processing.

#### End-to-end

The unit/integration suites above run in isolation (mocked collaborators). The
end-to-end suites run the **real** stack — a real NestJS app over HTTP, a real
Redis queue, a real browser against the real Next.js server — which is the only
way to catch the integration bugs those suites cannot (a broken global guard
order, a `Set-Cookie` the browser never sends, a cookie written while the page is
still streaming).

```bash
# API e2e — spins up the Nest app in memory; uses its OWN database (<name>_e2e),
# created and migrated by test/jest-e2e-setup.js, so it cannot wipe your dev data.
pnpm --filter api test:e2e

# Web e2e — builds api + worker, seeds the database, boots api + worker + web
# (Playwright `webServer`), then drives a real Chromium.
pnpm --filter web e2e
```

`apps/api` and `apps/worker` tests hit a real PostgreSQL database (`docker compose up -d` first, then `pnpm --filter api test` / `pnpm --filter worker test`).

The worker reads its own `apps/worker/.env` (it is a separate process from the API, so it does not inherit the API's). It needs `DATABASE_URL`, `REDIS_*` and — to generate reports — the same `REPORTS_DIR` the API uses. See `.env.example`.

### Continuous integration

`.github/workflows/ci.yml` runs on every push to `main` and every pull request,
against `postgres:16` and `redis:7` **service containers** (no `.env` file exists
in CI, so the workflow sets the environment explicitly).

| Job | Steps |
|-----|-------|
| `checks` | install → Prisma generate → `migrate deploy` → `pnpm type-check` → `pnpm lint` → `pnpm test` (Vitest: api, worker, web) |
| `e2e` | install → Prisma generate → `migrate deploy` → `pnpm --filter api test:e2e` (Jest + Supertest) → build api + worker → install Chromium → `pnpm --filter web e2e` (Playwright) → upload the Playwright report |

The two jobs each get their own service containers, so the `checks` job's database
and the `e2e` job's database never interfere.

```
                              └──────────────────────┘

                     ┌──────────────┐        ┌──────────────┐
                     │ Prometheus    │───────▶│ Grafana      │
                     │ (scrapes /api │        │ (dashboards, │
                     │  /v1/metrics) │        │  :3300)      │
                     └──────────────┘        └──────────────┘
```

Key points:

- **One origin.** nginx fronts *everything* the browser touches, so the app's
  same-origin `httpOnly` refresh cookie (see
  [How server rendering authenticates](#how-server-rendering-authenticates)) keeps
  working in production without CORS.
- **The web app owns the API surface.** `/api/v1/*` is a Next.js *rewrite* to the
  API and `/api/auth/*` is a Route Handler that re-homes the refresh cookie;
  the browser never talks to the API directly.
- **api vs worker.** The API *produce* BullMQ jobs; the worker *consumes* them.
  They share the report volume so the worker writes artifacts the API streams
  back on download.
- **Observability.** the API exposes `/api/v1/health` (dependency check, 200/503)
  and `/api/v1/metrics` (Prometheus text), scraped into Grafana.

### 开发流程

```bash
# Boot dependencies once
docker compose up -d

# Terminal A — backend + worker
pnpm dev                       # turbo: api (watch) + web (turbopack)
pnpm --filter worker dev       # BullMQ worker (separate process)

# Terminal B — verification gates (run before every commit)
pnpm type-check                # tsc --noEmit across all packages
pnpm lint                      # ESLint across all packages
pnpm test                      # Vitest: api (unit/integration) + worker + web
pnpm --filter api test:e2e     # Jest + Supertest over the real API
pnpm --filter web e2e          # Playwright over the real browser
```

典型改动循环：改代码 → `pnpm --filter <pkg> type-check && pnpm lint` → 改模块的
单测 → `pnpm test` → 涉及跨进程/浏览器行为时跑 e2e → 更新 README（重大功能）→
commits 交给 `.github/workflows/ci.yml` 的 `checks` + `e2e` 两道门。

> **跑测试前先停掉 `pnpm dev`。** 几个 Vitest 套件（`queue-invite-email`、
> `queue-report`、`domain-event-bridge`）会起一个真实 `Worker` 去消费 Redis
> 队列，用来验证 producer/consumer 契约。如果本机同时跑着 dev 的 worker，
> 它会把这个 job 抢走，测试就永远等不到（表现为 10s 超时）。同样地，这些
> 套件会 `cleanDatabase()`，跑完会清掉本地 seed 数据——重新执行
> `pnpm --filter api db:seed` 即可恢复 `admin@example.com / Admin123!`。
>
> Windows 上 `kill` 常只终止父进程，`node` 子进程会残留并继续占用队列；
> 用 `tasklist //FI "IMAGENAME eq node.exe"` 查出后逐个 `taskkill //F //PID <pid>`。

## 🚢 Production deployment

Production runs exactly one Compose stack — nginx, the web app, the API, the
worker, Postgres, Redis, Prometheus and Grafana — configured in
`docker-compose.prod.yml`. Each app ships a multi-stage `Dockerfile` that bakes
in only the runtime files and runs as a non-root user.

### Deployment steps

```bash
# 1. Create the production environment file and fill in the secrets.
cp .env.production.example .env.production
#    DATABASE_URL, JWT_SECRET, JWT_REFRESH_SECRET, POSTGRES_PASSWORD …
#    Generate JWT secrets with: openssl rand -base64 48

# 2. (From a checked-out repo) start the whole stack.
docker compose -f docker-compose.prod.yml up -d --build

# 3. Verify every service is healthy.
docker compose -f docker-compose.prod.yml ps

# 4. Apply pending migrations (also runs automatically at boot via the
#    one-shot `migrate` service).
docker compose -f docker-compose.prod.yml run --rm migrate
```

Order of operations inside Compose (all wired with `depends_on` +
`service_healthy` / `service_completed_successfully`):

```
postgres ──healthy──▶ migrate ──completed──▶ api ──healthy──▶ web ──healthy──▶ nginx
redis    ──healthy──▶ api (queue)            │                │
                     ▶ worker                └──healthy──▶ prometheus ──▶ grafana
```

**Before going live** terminate TLS at nginx (a host TLS proxy or certs mounted
into the nginx container) and point `FRONTEND_URL` / `NEXT_PUBLIC_SITE_URL` at the
public https origin — the app sets `Secure` cookies in production.

### Environment variables

`.env.production.example` documents every variable. The ones you must override:

| Variable | Service | Meaning |
|----------|---------|---------|
| `DATABASE_URL` | api, worker, migrate | `postgresql://` URL; hostname is the Compose service `postgres` |
| `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` | postgres | must match `DATABASE_URL` |
| `JWT_SECRET` / `JWT_REFRESH_SECRET` | api | token signing keys — random, ≥32 bytes, never shared between environments |
| `REDIS_URL` / `REDIS_HOST` / `REDIS_PORT` | api, worker | queue/cache/rate-limit backend (`redis` service) |
| `FRONTEND_URL` | api | CORS origin + OAuth redirect base (`https://app.example.com`) |
| `API_ORIGIN` | web | where the Next.js server calls the API (`http://api:3001`) |
| `NEXT_PUBLIC_SITE_URL` / `NEXT_PUBLIC_APP_URL` | web | public origin for absolute links/redirects |
| `SMTP_HOST` / `SMTP_PORT` / `SMTP_USER` / `SMTP_PASS` | api, worker | transactional email relay (Mailpit in dev) |
| `REPORTS_DIR` | api, worker | shared volume path (`/app/storage/reports`) both mounts must agree on |
| `GRAFANA_ADMIN_PASSWORD` | grafana | initial admin password; change on first login |

`cp .env.production.example .env.production` and commit nothing — `.env.production`
is gitignored.

### Health checks & monitoring

- **api** `GET /api/v1/health` — real DB + Redis pings; returns `200` when both
  are up and `503` otherwise, so orchestration fails the container instead of
  routing into a broken one.
- **web** `GET /api/healthz` — process liveness for the nginx upstream.
- **worker** — no HTTP surface; the container healthcheck is process liveness,
  and `restart: unless-stopped` recovers crashes.
- **api** `GET /api/v1/metrics` — Prometheus text (`http_requests_total`,
  `http_request_duration_bucket`), scraped at `http://localhost:9090`.
- **grafana** — pre-provisioned with the Prometheus datasource and an
  "SaaS API Overview" dashboard at `http://localhost:3300`.

### Logging

Every container uses the Docker `json-file` driver with rotation (10 MB × 5), so
`docker compose logs -f <service>` is the log viewing path. nginx writes access
logs to stdout with request time and forwards `X-Forwarded-*`; the app itself
logs to Nest/Next standard output, so no log files accumulate inside images.
